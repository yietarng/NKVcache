---
title: "Sub-Context KV Cache (NOC)"
metatags:
    description: "Position-independent KV reuse for repeated sub-contexts in agentic workloads."
---

Agentic sessions resubmit large fractions of their context every turn (tool
outputs, RAG fragments, system-prompt blocks) but RadixAttention's prefix
match only discovers reuse when a span recurs at the *same* offset from
position 0. This feature (internal name **NOC**) extends KV reuse to any
recurring sub-context, independent of position, by keying a chunk's cached
KV by content hash instead of tree path, and re-encoding it for its new
position instead of recomputing it.

## Status

The full mechanism described here is implemented, including the path that
excludes reused tokens from the live forward pass (previously a spec-only
section of this doc). What's verified without a GPU, and what still needs
GPU validation before production use, is called out per section below --
see "Implementation status" at the end for the summary.

## Algorithm

1. **Scan (CPU).** After the ordinary prefix-radix match, scan the
   unmatched suffix of the request's tokens against a content-addressed
   index of previously-computed sub-contexts. Two sources: explicit tags
   the caller attaches to the request (a tool-output span, a RAG fragment
   id, ...), and automatic detection via rolling-hash probing.
2. **Reposition.** A matched chunk's cached K was computed with RoPE baked
   in at its original position. RoPE's rotation composes additively
   (`Rot(p_new) = Rot(p_new - p_old) @ Rot(p_old)`), so the chunk's K is
   moved to its new position by rotating it once more by the offset delta
   -- no recomputation, no recovering the pre-rotation value. V carries no
   positional encoding and is copied as-is.
3. **Compute the rest from scratch.** Tokens not covered by any match
   (the "glue" between sub-contexts) go through a normal forward pass, as
   does a small selectively-recomputed subset of each match (see below).

## Why reuse alone is an approximation

Repositioning fixes a reused chunk's *position*, not its *content*: the
chunk's K/V were computed while attending to whatever preceded it the
first time it was seen, and now sit next to different neighbors. Following
CacheBlend/EPIC (`https://github.com/DerekHJH/epic`), a configurable
fraction of each chunk's tokens (`--subcontext-recompute-ratio`, default
0.15; the chunk's leading tokens, prefix-fraction policy) is forced through
a real forward pass instead of trusted as pure reuse, bounding the error.
Setting the ratio to 0 recovers pure PromptCache-style reuse.

## MVP scope

Restricted to dense, standard-RoPE models (e.g. Llama-style) without MLA,
mrope, SWA, Mamba, or the CUDA-graph fast path -- the surface where the
delta-rotation trick and the "exclude reused tokens from the forward pass"
batch construction are both straightforward. Wiring the remaining backends
is follow-up work, not a design limitation of the approach itself.

## Architecture

### Content-addressed index (`mem_cache/subcontext/`)

- `subcontext_types.py` -- `SubContextTag` (explicit boundary), `SubContextEntry`
  (a registered chunk: content hash, token ids, original position, KV-pool
  slot indices), `SubContextMatch` (one resolved hit in a new request),
  `RecomputePlan` (which offsets of a match get force-recomputed).
- `subcontext_index.py` -- `SubContextIndex`: sha256-content-hash keyed
  store with LRU eviction and refcounting (`inc_ref`/`dec_ref`, mirroring
  `RadixCache.inc_lock_ref`/`dec_lock_ref`) so a chunk locked by an
  in-flight request is never evicted out from under it. A probe-hash
  bucket (`PROBE_LEN`-token prefix hash) narrows scan candidates before a
  full verify.
- `subcontext_scanner.py` -- `scan(index, token_ids, explicit_tags, start)`:
  greedy, longest-match-first scan restricted to `token_ids[start:]` (the
  region *not* already covered by the ordinary prefix match, which is
  strictly cheaper reuse and always wins where it applies).
- `deviation_recompute.py` -- `plan_prefix_fraction` / `plan_none`: turns a
  match into a `RecomputePlan`.

**Tested**: `test/registered/unit/mem_cache/test_subcontext_cache.py` --
10 cases covering the scanner's longest-match and explicit-tag-priority
invariants, index refcount-blocks-eviction, and `RecomputePlan` boundary
math. Pure CPU/tensor logic, runs on any runner.

### RoPE delta-repositioning (`layers/rotary_embedding/reposition.py`)

`reposition_key(cached_key, delta_positions, inv_freq, is_neox_style)`
recomputes cos/sin directly from `delta_positions * inv_freq` (rather than
indexing the model's position-capped cache, since a delta can be negative)
and reapplies `apply_rotary_emb` on top of the already-rotated K. Callers
pass only the rotary slice for partial-rotary models.

**Tested**: rotation composition (`Rot(delta) @ Rot(p_old) == Rot(p_old +
delta)`, both NeoX and GPT-J styles) verified numerically against the
repo's real `apply_rotary_emb`, plus the zero-delta identity case.

### Explicit tagging API

`GenerateReqInput.subcontext_tags` (a list of `{"subcontext_id", "start",
"end"}`, token offsets into the request's own tokens) flows through
`TokenizedGenerateReqInput.subcontext_tags` (`managers/io_struct.py`,
`managers/tokenizer_manager.py`) into `Req.subcontext_tags`
(`managers/schedule_batch.py`). Ignored entirely unless
`--enable-subcontext-kv-cache` is set.

### CLI flags (`arg_groups/fields/memory.py`)

- `--enable-subcontext-kv-cache` (default off)
- `--subcontext-recompute-ratio` (default 0.15)

Per the env-var-conventions skill, these are CLI flags (user-facing,
expected to be documented and flipped per deployment), not env vars.
Verified end-to-end: `ServerArgs.add_cli_args` / `from_cli_args` parse both
flags and resolve them onto the flat `ServerArgs` object.

### Scheduler-side matching (`managers/schedule_batch.py`)

`Req.init_next_round_input` gained `subcontext_index` and
`subcontext_recompute_ratio` parameters (both optional, default off, so
every existing call site is unaffected). When a `SubContextIndex` is
passed and the request has unmatched suffix tokens, it resolves
`self.subcontext_tags` into `SubContextTag`s, scans the unmatched suffix,
and stores the result on the request as `req.subcontext_matches` /
`req.subcontext_recompute_plans`.

**Verified**: `schedule_batch.py`, `scheduler.py`, `tokenizer_manager.py`,
and `server_args.py` all import cleanly end-to-end with this change (full
CPU dependency chain resolved and exercised in this repo's sandbox,
without GPU/CUDA) -- the wiring is syntactically and structurally sound
end to end from the HTTP request field down to the per-request match plan.

## How reused tokens are excluded from the live forward pass

This is the mechanism that makes the feature actually save compute rather
than just relabel it -- prefix caching already skips the full per-layer
forward (not just the attention math) for cached tokens, and this
generalizes that to non-leading spans. Two things happen, in order, for a
batch containing subcontext-matched requests:

1. **Materialize reused KV before the model forward.**
   `ScheduleBatch.prepare_for_extend` (`managers/schedule_batch.py`) computes,
   per eligible request, a `RequestSubcontextPlan`
   (`mem_cache/subcontext/extend_plan.py: plan_request_extend`) splitting its
   extend range into `surviving_local` offsets (need a real forward pass)
   and `reused_local` offsets (materialized instead), then
   `build_batch_subcontext_plan` applies that split to the batch's
   already-allocated `out_cache_loc` (allocation itself is untouched --
   sized off the *full* logical range, since every position needs a slot
   either way) and collects a flat `SubcontextMaterializePlan`
   (source slot, dest slot, delta position per reused token) onto
   `batch.subcontext_materialize_plan`. `managers/tp_worker.py:
   forward_batch_generation` calls
   `kv_materialize.materialize_reused_kv_for_batch` with it right after
   `ForwardBatch.init_new(...)` and before `self.model_runner.forward(...)`:
   for every layer, gather the source chunk's K/V via
   `KVCache.get_key_buffer(layer_id)` / `get_value_buffer(layer_id)`,
   reposition K (`layers/rotary_embedding/reposition.py`), and
   `index_copy_` both into the destination slots. Pure data movement, no
   model forward involved, so `model_executor/model_runner.py` (frozen)
   does not change.
2. **Exclude those tokens from the forward pass.** In the same
   `prepare_for_extend` pass, `input_ids` becomes a *gather* over each
   eligible request's `surviving_absolute` positions instead of the plain
   `fill_ids[prefix_len:]` slice, and `extend_lens` /
   `extend_num_tokens` are rebound to the surviving-token counts
   (allocation already happened off the full counts, so this rebind is
   safe). `batch.subcontext_positions` carries the true logical positions
   for those surviving tokens; `ForwardBatch.init_new`
   (`model_executor/forward_batch_info.py`) overrides `ret.positions` with
   it in the same branch that already handles DLLM/spec-info position
   overrides, ahead of the default `compute_position()` arange (which
   still runs, correctly sized off the now-consistent `extend_lens`, but
   is simply discarded). `req_to_token_pool`'s row for each request already
   holds every logical position's slot after allocation regardless of
   which step (materializer or live forward) later fills it, so existing
   attention backends need no change -- they already attend over the full
   row up to `seq_len` (confirmed against `flashattention_backend.py`,
   which derives `cu_seqlens_q` from `extend_seq_lens` and the KV context
   length separately from `seq_lens`, exactly the split this needs).

**Eligibility gate.** `prepare_for_extend` only takes this path for a
request with a non-empty `subcontext_recompute_plans`, no multimodal
inputs, no positional-embed overrides, and only when the whole batch has
`return_logprob=False`, isn't DLLM, and isn't running the mamba extra
buffer -- deliberately conservative so the untouched path (unaffected by
any of this) is guaranteed to run for anything the accounting above
doesn't cover. Below the request level, `reused_ranges_within` also drops
any match that isn't *entirely* inside the current extend range, so a
match split across a chunked-prefill boundary is just computed normally
rather than partially materialized.

**Zero-overhead-when-idle.** Every new code path in `prepare_for_extend` is
gated behind `subcontext_active = any(plan is not None for plan in
subcontext_request_plans)`, itself impossible to be `True` unless a
`SubContextIndex` was constructed (`--enable-subcontext-kv-cache`) *and* a
request actually matched something. Feature off, or on with nothing yet
recurring, is byte-for-byte the pre-existing code path --
`test_build_batch_subcontext_plan_all_passthrough_matches_original`
pins this down for the batch-plan transform itself.

**Startup validation.** `Scheduler.maybe_init_subcontext_index`
(`managers/scheduler.py`) resolves the loaded model's `RotaryEmbedding` via
`kv_materialize.find_rotary_embedding` and raises at startup if the model
doesn't have exactly one shared instance (mixed RoPE bases, MLA, mrope,
NoPE/ALiBi) -- the MVP's dense/standard-RoPE restriction is enforced, not
just documented.

## What still needs GPU validation

Every module above is either pure-CPU tested (index, scanner, rotation
math, materializer against a fake pool, the batch-plan transform) or
import/syntax verified end-to-end (this repo's real dependency chain,
resolved in a CPU-only sandbox, imports `schedule_batch.py`, `scheduler.py`,
`tp_worker.py`, `forward_batch_info.py`, `tokenizer_manager.py`, and
`server_args.py` cleanly with these changes). What that cannot cover: an
actual forward pass on a real dense model, confirming the attention
backend's `cu_seqlens_q`/context-length split behaves as analyzed under
`extend_seq_lens[i] != seq_lens[i] - prefix_lens[i]` -- the first time this
codebase produces that inequality for a plain (non-chunked, non-retracted)
extend batch. Recommended smoke test before any real traffic: a small
Llama-style model, a handful of requests that share an explicitly-tagged
sub-context at different offsets, `--subcontext-recompute-ratio 0` (pure
reuse, easiest to reason about), comparing output logits against the same
prompts run without `--enable-subcontext-kv-cache` for a byte-level baseline.
